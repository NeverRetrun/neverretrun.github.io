我觉得 Scope 是个坏模式

cvoid
2022-01-24

这里前提一下 Scope 是什么。可以阅读这边的文档 Laravel Scope。

在示例中的代码看起来非常的美好，通过封装查询条件让查询变得更加语义化。我也是因为看到这么美好的封装然后尝试使用了一下，其实体验非常的不好。

因为 Scope 的代码可能比较多，我不可能写在 Model 中，但是 Model 需要这些方法，我通过 Trait 这种方法放置 Scope，类似下方的这样。

然后第一个问题来了。我写链式查询的时候代码提示怎么来的，这里我是通过 laravel-ide-helper 这个扩展来生成注释的。生成后大概是这样的。

我相信很多人都是这样做的，因为这样确实得到了代码提示，也能够正常的工作。这种注释其实存在很大的隐患，其实所有的查询方法只会返回 Builder 这个类，写联合类型完全是因为要获取 User 这个类生成其他 Scope 方式，导致了注释的返回类型只能这么写。在你写动态 PHP 的时候完全没有问题，但是你一旦引入 PHPStan 或者 Psalm 这种静态分析的时候，噩梦就出现了。你没有办法解释为什么这里需要出现返回 User 类，导致只能忽略这些错误，但是数据库查询出来的值影响太多地方了，类似于下面这种情况。

这其实就是第一个问题，Scope 生成的代码注释没有处理好静态分析。
Scope 的第二个问题，这其实是有封装带来的恐慌，我没有办法第一眼直观的看出这个 SQL 到底做了些什么？可能我 debug 代码需要非常多的跳转，因为我跳转是到对应的 Model 类注释方法上面，而不是具体实现的 Scope 方法。如果是用 Trait 实现，那我还需要到 Trait 类，再全局查询方法名称。这显然是有问题的。

然后我还思考了一个问题，Scope 的本质是封装查询条件让查询更方便。那如果你使用了 DAO 或者 Repository 这种分层，那 Scope 还有意义么？
我觉得是没有的，完全没有意义。因为复用了查询，那复用查询条件的次数就会大大降低。我观察我之前写的 Scope 最多复用次数都不会超过 3 次。

我觉得 Scope 这种模式对我用处不大，而且我觉得这个博主封装查询条件的思路更好，更加静态化，没有我说的上述所有的问题。
